# Harmonic Engine — будущие уточнения и расширения

Этот файл фиксирует музыкальные пробелы и архитектурные наблюдения, обнаруженные уже после принятия stable `0.3` / Stage 2. Они не считаются регрессиями текущей стабильной версии и не должны скрыто вноситься в UI- или Improvisation Engine checkpoints.

Связанный backlog: Issue #29.

## 1. Минорный оборот iv–V–i

Во время live-test `0.3e-ui` обнаружен классический случай в `C minor`:

```text
Fm7 → G7 → Cm7
iv7 → V7 → i7
```

Функциональная логика:

```text
Субдоминанта → Доминанта → Тоника
```

Текущий Pattern Recognizer Stage 2 знает minor `iiø–V–i`, но отдельного `HarmonicPatternType` / правила для minor `iv–V–i` нет. Поэтому при курсоре на `Fm7` UI корректно показывает функцию **Субдоминанта** и материал `F Dorian • Fm6`, но строка гармонического оборота остаётся `не распознан`.

Это пробел каталога паттернов, а не ошибка Improvisation Engine.

### Будущее ожидаемое поведение

На `Fm7`:

```text
Функция: Субдоминанта
Оборот: Минорный iv–V–i • 1 / 3
Мышление: F Dorian • Fm6
```

На `G7` при полном окне `Fm7 → G7 → Cm7`:

```text
Функция: Доминанта
Оборот: Минорный iv–V–i • 2 / 3
```

На `Cm7`:

```text
Функция: Тоника
Разрешение: V→i
```

Конкретный predominant (`iiø` или `iv`) на последней позиции можно утверждать только при достаточном количестве исторических evidence.

## 2. Ограничение Stage 1 contract: previous / current / next

Harmonic Engine получает только:

```text
previous chord
current chord
next chord
global key
```

Это намеренно компактный host-neutral контракт Stage 1.

Следствие: на последнем `i` в последовательностях

```text
Dm7b5 → G7 → Cm
Fm7   → G7 → Cm
```

текущий snapshot выглядит одинаково по ближайшему окружению:

```text
previous = G7
current  = Cm
```

Поэтому движок уже не может достоверно определить, какой именно predominant предшествовал доминанте. Нельзя без дополнительных evidence автоматически маркировать любое `V→i` как конкретный трёхаккордовый `iiø–V–i` или `iv–V–i`.

### Предлагаемая семантика

- когда видны все три аккорда — распознавать конкретный трёхаккордовый паттерн;
- на boundary `iv → V` — разрешить candidate `iv–V–i`;
- на boundary `iiø → V` — сохранять существующий candidate `iiø–V–i`;
- на `V → i` без более глубокой истории — показывать более общий `V–i / resolution` либо сохранять ambiguity;
- не подменять отсутствие evidence догадкой.

Это особенно важно перед `0.3f — Context-aware ranking / ambiguity`.

## 3. Regression-набор для будущей доработки

Добавить минимум следующие тесты:

```text
C minor: Fm7 → G7 → Cm7
C minor: Dm7b5 → G7 → Cm7
C minor: G7 → Cm7, previous predominant недоступен
```

Проверить:

- корректные функции `S / D / T`;
- позиции `1 / 3`, `2 / 3` только при достаточном контексте;
- отсутствие ложного утверждения конкретного predominant на `i`;
- отсутствие регрессии существующего minor `iiø–V–i`;
- корректное взаимодействие с global/local/ambiguous interpretations;
- сохранение Stage 1 contract, если расширение истории не будет принято отдельным архитектурным решением.

## 4. Граница текущей разработки

Не включать это изменение скрыто в `0.3e-ui`: текущий checkpoint занимается presentation layer и не должен менять музыкальный анализ.

Реализацию делать отдельной будущей задачей Harmonic Engine / Pattern Recognizer с явным checkpoint и live-test.
