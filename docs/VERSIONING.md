# Smart Improviser — Versioning

Этот документ фиксирует официальную схему версионирования Smart Improviser.

## Основной принцип

Разработка организована по этапам `Stage`.

Каждый Stage начинается с буквенной рабочей версии и заканчивается стабильной числовой версией без буквенного суффикса.

Пример для Stage 0:

```text
0.0a
→ 0.0b
→ 0.0c
→ ...
→ 0.1
```

Где:

- `0.0a` — начальная рабочая версия Stage 0;
- `0.0b`, `0.0c`, ... — следующие завершённые подэтапы внутри Stage 0;
- `0.1` — итоговая версия после полного завершения Stage 0.

После этого Stage 1 начинается с:

```text
0.1a
```

и завершается:

```text
0.2
```

## Правило буквенных версий

Буква обозначает следующий логически завершённый подэтап внутри текущего Stage.

Пример:

```text
Stage 0

0.0a — первый рабочий фундамент
0.0b — следующий подэтап
0.0c — следующий подэтап
...
0.1  — весь Stage 0 завершён
```

Буква меняется не на каждый commit, а после завершения отдельного проверяемого подэтапа.

## Правило fix-версий

Если конкретная буквенная версия дошла до живого тестирования и в ней обнаружена ошибка, версия не переводится сразу на следующую букву.

Для исправления используется суффикс:

```text
fixN
```

Пример:

```text
0.0b
0.0b fix1
0.0b fix2
```

После успешного исправления и перехода к следующему подэтапу:

```text
0.0c
```

То есть `fix` означает исправление уже существующего подэтапа, а новая буква — новый подэтап разработки.

## Полный пример жизненного цикла Stage

```text
0.0a
↓
0.0b
↓
живой тест обнаружил проблему
↓
0.0b fix1
↓
повторный тест обнаружил ещё одну проблему
↓
0.0b fix2
↓
подэтап принят
↓
0.0c
↓
...
↓
Stage 0 полностью завершён
↓
0.1
```

## Соответствие Stage и итоговых версий

| Stage | Рабочая линия | Итоговая версия |
|---|---|---|
| Stage 0 | `0.0a`, `0.0b`, ... | `0.1` |
| Stage 1 | `0.1a`, `0.1b`, ... | `0.2` |
| Stage 2 | `0.2a`, `0.2b`, ... | `0.3` |
| Stage 3 | `0.3a`, `0.3b`, ... | `0.4` |
| Stage 4 | `0.4a`, `0.4b`, ... | `0.5` |
| Stage 5 | `0.5a`, `0.5b`, ... | `0.6` |
| Stage 6 | `0.6a`, `0.6b`, ... | `0.7` |

## Что считается версией

Версия присваивается проверяемому состоянию проекта, а не отдельному commit.

Обычные commits внутри работы над одним подэтапом не меняют буквенную версию автоматически.

Например несколько commits могут относиться к одной версии:

```text
0.0b
```

пока соответствующий подэтап не завершён.

## Живые тесты

Если версия предназначена для проверки в Fender Studio Pro или другой реальной среде, имя сборки должно сохранять буквенную/fix-версию.

Примеры:

```text
Smart Improviser 0.0a
Smart Improviser 0.0b
Smart Improviser 0.0b fix1
Smart Improviser 0.1
```

Это позволяет однозначно связать:

- конкретную сборку;
- результаты ручного тестирования;
- GitHub Issue/PR;
- исправления;
- итог Stage.

## Правило для GitHub Issues

Каждый Stage Issue должен содержать диапазон версий этапа.

Например:

```text
Stage 0
Working: 0.0a → 0.0x
Final: 0.1
```

При переходе к новому подэтапу в Issue отмечается соответствующий checklist и текущая буквенная версия.

Если появляется `fixN`, в Issue должно быть понятно, какая именно проблема потребовала fix-сборку и какой тест подтвердил исправление.
