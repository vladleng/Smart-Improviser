# Smart Improviser — Versioning

Этот документ фиксирует официальную схему версионирования Smart Improviser.

## Основной принцип

Разработка организована по этапам `Stage`.

Каждый Stage **обязательно делится на логически завершённые подэтапы**. Каждому такому подэтапу соответствует отдельная буквенная build-версия.

Stage начинается с буквенной рабочей версии и заканчивается стабильной числовой версией без буквенного суффикса.

Пример для Stage 0:

```text
0.0a
→ 0.0b
→ 0.0c
→ ...
→ 0.1
```

Где:

- `0.0a` — первый логический подэтап Stage 0;
- `0.0b`, `0.0c`, ... — следующие логические подэтапы;
- `0.1` — итоговая версия после полного завершения Stage 0.

После этого Stage 1 начинается с:

```text
0.1a
```

и завершается:

```text
0.2
```

## Обязательное правило декомпозиции Stage

Stage не должен разрабатываться как одна большая рабочая версия.

Перед началом или в самом начале нового Stage его объём разбивается на отдельные проверяемые подэтапы. Каждый подэтап должен:

- иметь одну понятную техническую или музыкальную цель;
- давать проверяемый результат;
- иметь собственный набор regression/live tests, если они применимы;
- иметь собственную буквенную build-версию;
- быть отражён в Stage Issue;
- быть принят до перехода к следующей буквенной версии.

Пример:

```text
Stage 2 — Harmonic Engine

0.2a — Harmonic Engine foundation
0.2b — Pattern Recognizer
0.2c — Tritone Substitution
0.2d — Local Key Center
0.2e — Ambiguity / Confidence
0.2f — Integration / musical validation
0.3  — Stage 2 complete
```

Конкретное количество буквенных подэтапов заранее не фиксируется навсегда. План может уточняться по мере разработки, но **каждая новая логически самостоятельная часть Stage получает новую буквенную версию**.

Нельзя использовать одну буквенную версию для всего Stage только ради сокращения числа билдов.

## Буквенная версия = build checkpoint

Каждая буквенная версия является самостоятельным build checkpoint.

Это означает, что для неё по возможности фиксируются:

- внутренний build version;
- GitHub Actions artifact;
- соответствующий checklist в Stage Issue;
- regression tests;
- при необходимости live-test report;
- точка возврата при regression.

Например:

```text
0.2a
→ Smart-Improviser-0.2a-Windows

0.2b
→ Smart-Improviser-0.2b-Windows
```

Обычные commits внутри работы над одним подэтапом не создают новую буквенную версию.

## Правило буквенных версий

Буква обозначает следующий логически завершённый подэтап внутри текущего Stage.

Пример:

```text
Stage 0

0.0a — первый рабочий фундамент
0.0b — следующий подэтап
0.0c — следующий подэтап
...
0.1  — весь Stage 0 завершён
```

Буква меняется не на каждый commit, а после завершения отдельного проверяемого подэтапа.

Переход:

```text
0.2a → 0.2b
```

означает, что `0.2a` принят и начинается **новая функциональная часть Stage**, а не просто очередной commit.

## Правило fix-версий

Если конкретная буквенная версия дошла до живого тестирования или CI/regression validation и в ней обнаружена ошибка, версия не переводится сразу на следующую букву.

Для исправления используется суффикс:

```text
fixN
```

Пример:

```text
0.2b
0.2b fix1
0.2b fix2
```

После успешного исправления и принятия текущего подэтапа можно перейти к следующему:

```text
0.2c
```

То есть:

- `fixN` — исправление уже существующего подэтапа;
- новая буква — новый логический подэтап разработки.

`fixN` не должен использоваться для добавления новой функциональности, которая относится к следующему подэтапу.

## Полный пример жизненного цикла Stage

```text
0.2a
↓
подэтап принят
↓
0.2b
↓
живой тест обнаружил проблему
↓
0.2b fix1
↓
повторный тест обнаружил ещё одну проблему
↓
0.2b fix2
↓
подэтап принят
↓
0.2c
↓
...
↓
Stage 2 полностью завершён
↓
0.3
```

## Соответствие Stage и итоговых версий

| Stage | Рабочая линия | Итоговая версия |
|---|---|---|
| Stage 0 | `0.0a`, `0.0b`, ... | `0.1` |
| Stage 1 | `0.1a`, `0.1b`, ... | `0.2` |
| Stage 2 | `0.2a`, `0.2b`, ... | `0.3` |
| Stage 3 | `0.3a`, `0.3b`, ... | `0.4` |
| Stage 4 | `0.4a`, `0.4b`, ... | `0.5` |
| Stage 5 | `0.5a`, `0.5b`, ... | `0.6` |
| Stage 6 | `0.6a`, `0.6b`, ... | `0.7` |
| Stage 7 | `0.7a`, `0.7b`, ... | `0.8` |
| Stage 8 | `0.8a`, `0.8b`, ... | `0.9` |
| Stage 9 | `0.9a`, `0.9b`, ... | `1.0` |
| Stage 10 | `1.0a`, `1.0b`, ... | `1.1` |

## Что считается версией

Версия присваивается проверяемому состоянию проекта, а не отдельному commit.

Обычные commits внутри работы над одним подэтапом не меняют буквенную версию автоматически.

Например несколько commits могут относиться к одной версии:

```text
0.2b
```

пока соответствующий подэтап не завершён.

## Живые тесты

Если версия предназначена для проверки в Fender Studio Pro или другой реальной среде, буквенная/fix-версия фиксируется во внутреннем build version и в имени GitHub Actions artifact.

Примеры artifact:

```text
Smart-Improviser-0.2a-Windows
Smart-Improviser-0.2b-Windows
Smart-Improviser-0.2b-fix1-Windows
```

### Постоянное имя устанавливаемого VST3 package

Начиная с Stage 1 все готовые Windows-сборки выдаются как одна и та же устанавливаемая папка:

```text
Smart Improviser.vst3
```

Имя `Smart Improviser.vst3` **не содержит номер версии** и не меняется между буквенными, `fixN` и финальными версиями.

Это сделано специально, чтобы ручной тест выполнялся простой заменой предыдущей папки в системной директории VST3:

```text
старый Smart Improviser.vst3
        ↓ заменить
новый Smart Improviser.vst3
```

Версия конкретной сборки определяется по имени скачанного GitHub Actions artifact и внутреннему build version, а не по имени установленной VST3-папки.

Это позволяет однозначно связать:

- конкретный логический подэтап;
- конкретную сборку;
- результаты ручного тестирования;
- GitHub Issue/PR;
- исправления;
- итог Stage;
- при этом сохранить постоянный drop-in package для установки.

## Правило для GitHub Issues

Каждый Stage Issue должен содержать:

1. диапазон версий Stage;
2. план логических подэтапов;
3. соответствие каждого подэтапа буквенной версии;
4. checklist текущего подэтапа;
5. критерий принятия текущей build-версии;
6. общий критерий завершения Stage.

Пример:

```text
Stage 2
Working: 0.2a → 0.2x
Final: 0.3

0.2a — Foundation
0.2b — Pattern Recognizer
0.2c — Tritone Substitution
...
```

При переходе к новому подэтапу в Issue отмечается соответствующий checklist и текущая буквенная версия.

Если появляется `fixN`, в Issue должно быть понятно:

- какая проблема потребовала fix-сборку;
- какая версия исправляется;
- какой тест подтвердил исправление.

## Правило для планирования следующих Stage

Перед началом Stage следующий рабочий чат/PR должен сначала определить его логические подэтапы и назначить им буквенные версии.

Допускается уточнять порядок или добавлять новые подэтапы по ходу работы, если обнаружилась отдельная функциональная задача. В таком случае она получает следующую свободную буквенную версию, а roadmap/Issue обновляются.
